# VELOR AI — Аудит AI-архитектуры и план внедрения мультипровайдерности

> Статус: аналитический документ. Код НЕ изменён. Реализация — только после одобрения плана.
> Дата: 2026-08-01

---

## 0. Краткое резюме (TL;DR)

- Вся работа с языковой моделью в проекте проходит через **одну функцию** — `_ask()` в [`ai.py`](ai.py). Это огромное преимущество: AI Router внедряется в одну точку, не трогая ~25 мест вызова.
- Сейчас поддерживается 2 провайдера (Claude + GigaChat), но выбор жёстко зашит в модуле на уровне **всей платформы**, а не бизнеса. Ключи — глобальные из `.env`, единые для всех тенантов.
- RAG — примитивный (поиск по совпадению слов, без эмбеддингов), инжектится в промпт через `_docs_block` / `_knowledge_block`. Работает, менять в первую очередь не требуется.
- Мультипровайдерность и «ключи пользователей» внедряются **поэтапно и обратно совместимо**: пока в БД нет ключа бизнеса — используется текущий глобальный путь. Ничего не ломается.
- Главные риски: глобальное состояние `_active`, отсутствие изоляции ключей по тенантам, отсутствие шифрования ключей. Все три решаемы без переписывания.

## 1. Текущая архитектура

### 1.1 Как происходит вызов языковой модели

Единый конвейер, всё централизовано в [`ai.py`](ai.py):

```
server.py / bot.py / botcore.py / signals.py / exporters.py
        │  (≈25 мест вызова: chat_reply, assistant_answer, find_risks, board_recommendations, …)
        ▼
   публичная функция в ai.py  (собирает system-промпт)
        ▼
   _ask(system, messages, max_tokens)          ← ЕДИНАЯ ТОЧКА ВЫЗОВА LLM
        ▼
   _providers()  → [("claude", _claude_chat), ("gigachat", _giga_chat)]
        ▼
   провайдер-функция: _claude_chat / _giga_chat
        ▼
   Anthropic SDK  /  requests → GigaChat REST
```

Ключевые факты:
- **`_ask()`** ([ai.py:661](ai.py)) перебирает провайдеров по порядку, при ошибке падает на следующего (failover). Работающий провайдер запоминается в module-level переменной **`_active`** ([ai.py:33](ai.py)) и поднимается вперёд в очереди.
- **`_providers()`** ([ai.py:632](ai.py)) строит список из того, что настроено: `_claude` (создан при импорте, если есть `ANTHROPIC_API_KEY`) и `GIGACHAT_AUTH_KEY`.
- **`ping()`** ([ai.py:648](ai.py)) при старте определяет живого провайдера.
- **`ai_available()`** ([ai.py:644](ai.py)) — есть ли хоть один провайдер; используется как gate почти во всех эндпоинтах.

### 1.2 Где формируется системный промпт

Промпты формируются **только внутри `ai.py`**, децентрализованно по функциям:
- Диалоговые сборщики: `_system_chat` ([ai.py:95](ai.py)), `_system_assistant` ([ai.py:179](ai.py)), `_system_site` ([ai.py:546](ai.py)).
- Личность/тон/роль: `_identity`, `_tone_line`, `_ROLE_PERSONA`.
- ~15 специализированных функций несут собственный inline system-промпт: `find_opportunities`, `board_recommendations`, `generate_ideas`, `find_risks`, `journal_entry`, `morning_briefing`, `weekly_review`, `client_summary`, `categorize_operations`, `parse_search_query`, `search_answer`, `finance_insights`, `analyze_content`, `generate_content`, `competitor_analysis`, `goal_actions`.
- Общий «RAG-в-контексте»: `_knowledge_block` ([ai.py:52](ai.py)) и `_docs_block` ([ai.py:82](ai.py)) подмешиваются в большинство промптов.

### 1.3 Где происходит RAG

Двухслойный, оба слоя — «инъекция в контекст», без векторов:
1. **База знаний бизнеса** — поле `businesses.knowledge` + `facts` (из `memory_facts`), целиком (обрезка `[:4000]`) кладётся в промпт через `_knowledge_block`.
2. **Документы** — retrieval в [`database.search_chunks()`](database.py) ([database.py:2463](database.py)): наивный скоринг по числу совпадений слов (≥4 символа) над `doc_chunks`. Топ-k чанков → `_docs_block` → промпт.
   - Загрузка/чанкинг: `add_document` + `_chunk_text` ([database.py:2386](database.py)), чанки ~600 симв. по границам предложений.
   - Вызывается в `botcore.py:60` (диалог с клиентом) и `server.py:2419` (ассистент в кабинете).

Векторного поиска/эмбеддингов **нет** — и для MVP этого достаточно.

### 1.4 Хранение ключей и настроек сейчас

- Ключи — **глобальные, из `.env`** через [`config.py`](config.py): `ANTHROPIC_API_KEY`, `GIGACHAT_AUTH_KEY`, `CLAUDE_MODEL`. Единые для всей платформы, **не** per-tenant.
- Клиент Anthropic создаётся один раз при импорте модуля ([ai.py:28](ai.py)).
- Настройки бизнеса живут в таблице `businesses` (много колонок добавлено миграциями в [database.py:218](database.py)): `knowledge`, `tone`, `ai_name`, `ai_traits`, `ai_desc` и т.д. Колонок под AI-провайдер/ключи **нет**.

## 2. Проблемы текущей архитектуры

| # | Проблема | Последствие | Критичность |
|---|----------|-------------|-------------|
| P1 | Выбор провайдера — глобальный, не per-business | Нельзя дать бизнесу свой провайдер/модель/ключ | Высокая (блокер фичи) |
| P2 | Ключи только в `.env`, единые на всех | Все тенанты жгут твой баланс; нет BYOK | Высокая |
| P3 | Глобальное состояние `_active` | При гонках/многотенантности провайдер «залипает»; тестировать тяжело | Средняя |
| P4 | Клиент Claude создаётся на импорте по одному ключу | Нельзя переключать ключ/модель в рантайме | Средняя |
| P5 | Нет учёта стоимости/лимитов по бизнесу | Невозможно тарифицировать AI-потребление | Средняя |
| P6 | Ключи, если появятся в БД, будут в открытом виде | Утечка = компрометация чужих аккаунтов LLM | Высокая (для BYOK) |
| P7 | RAG наивный (без эмбеддингов) | На больших базах падает релевантность | Низкая (не сейчас) |
| P8 | Провайдеры зашиты списком, нет реестра | Добавление OpenAI/YandexGPT/локальной = правка ядра | Средняя |

## 3. Предлагаемая новая архитектура

Принцип: **не переписывать, а обернуть**. `_ask()` остаётся единственной точкой, но получает за собой слой Router + Registry.

### 3.1 Слой провайдеров (Provider Registry)

Новый модуль `ai_providers.py` — единый интерфейс:

```
class Provider(Protocol):
    name: str
    def chat(self, system, messages, max_tokens, *, api_key, model) -> str: ...

REGISTRY = {"claude": ClaudeProvider(), "gigachat": GigaChatProvider(),
            "openai": OpenAIProvider(), "yandex": YandexProvider(), ...}
```

Существующие `_claude_chat` / `_giga_chat` переезжают сюда как реализации `Provider.chat` — **логика та же**, лишь принимают `api_key`/`model` аргументами вместо глобалей.

### 3.2 AI Router

Новый модуль `ai_router.py`. Функция `resolve(business, task) -> [ProviderChoice]` возвращает упорядоченный список (провайдер, ключ, модель) с failover:

Приоритет разрешения (первый непустой побеждает):
1. **Ключ/провайдер бизнеса** из БД (BYOK) — если задан и валиден.
2. **Правило по задаче** (напр. дешёвая модель для `categorize_operations`, умная для `board_recommendations`) — опционально, этап 3+.
3. **Глобальный дефолт** из `.env` — **текущее поведение** (обратная совместимость).

`_ask()` меняется минимально: вместо `_providers()` дергает `ai_router.resolve(business, task)`. Если бизнес не передан или в БД пусто — Router возвращает ровно сегодняшнюю глобальную цепочку.

> Важно: сигнатуры публичных функций `ai.py` уже принимают `business` — прокинуть его в `_ask` дёшево. Функции без бизнеса (`parse_search_query`) работают на глобальном дефолте.

### 3.3 Хранение ключей пользователей

- Отдельная таблица `ai_credentials` (не «толстая» `businesses`): `business_id, provider, api_key_enc, model, is_active, created_at`.
- **Шифрование в покое**: `cryptography.Fernet`, мастер-ключ `AI_KEYS_SECRET` из `.env` (как уже сделано для JWT-секрета). В API ключ никогда не отдаётся назад — только маскированный хвост (`sk-…abc`).
- Ввод ключа — **только пользователем локально в кабинете**, никогда через чат (согласно правилу проекта о секретах).

### 3.4 UI

- Новая страница `web/ai-settings.html` (или секция на существующей `settings.html`/`integrations.html`): выбор провайдера, ввод своего ключа, выбор модели, кнопка «Проверить» (пинг), индикатор активного провайдера и режима (BYOK / платформенный).

## 4. Поэтапный план внедрения

Каждый этап — самостоятельно рабочий и тестируемый, ничего не ломает.

### Этап 0 — Подготовка (рефакторинг без смены поведения)
- Вынести `_claude_chat`/`_giga_chat` в `ai_providers.py` с сигнатурой `chat(system, messages, max_tokens, api_key, model)`.
- `_ask()` продолжает звать их через тонкую обёртку с глобальными ключами.
- **Тест:** весь текущий функционал работает идентично (TestClient + пинг обоих провайдеров). Поведение не изменилось.

### Этап 1 — Router поверх глобального дефолта
- Ввести `ai_router.py`; `resolve()` пока возвращает только глобальную цепочку из `.env`.
- Убрать/инкапсулировать глобальный `_active` внутрь Router (per-call, не module-level).
- **Тест:** failover Claude→GigaChat работает как раньше; поведение идентично.

### Этап 2 — Хранилище ключей (без включения в проде)
- Миграция: таблица `ai_credentials` (idempotent, как остальные ALTER в `database.py`).
- Шифрование Fernet + `AI_KEYS_SECRET`. CRUD-функции в `database.py`.
- Router читает ключ бизнеса, **но фича-флаг `AI_BYOK_ENABLED=false`** — пока не влияет на прод.
- **Тест:** миграция проходит на пустой и заполненной БД; при выключенном флаге поведение прежнее.

### Этап 3 — UI и включение BYOK
- Страница `web/ai-settings.html`: выбор провайдера/модели, ввод ключа, «Проверить».
- Эндпоинты в `server.py`: GET (маскированно) / POST / DELETE / ping. Учесть trial read-only gate.
- Включить `AI_BYOK_ENABLED=true`. Бизнес без своего ключа → глобальный дефолт (совместимость).
- **Тест:** бизнес с ключом ходит на свой провайдер; без ключа — на платформенный.

### Этап 4 — Расширение реестра провайдеров (по необходимости)
- Добавить OpenAI / YandexGPT / локальную модель как новые `Provider` в реестр — **без правок ядра**.
- **Тест:** каждый новый провайдер пингуется и отвечает изолированно.

### Этап 5 (опционально, позже) — маршрутизация по задачам и учёт стоимости
- Правила «дешёвая модель для рутины, умная для аналитики».
- Логирование токенов/стоимости per business → тарификация.

## 5. Оценка рисков

| Риск | Вероятность | Влияние | Митигация |
|------|-------------|---------|-----------|
| Регресс в failover при рефакторинге `_ask` | Средняя | Высокое | Этап 0/1 без смены поведения + тесты до/после |
| Гонки из-за `_active` при многотенантности | Средняя | Среднее | Убрать module-level state, состояние per-call |
| Утечка ключей бизнесов | Низкая | Критическое | Шифрование Fernet, ключ не возвращается в API, маскирование |
| Сломать миграцию БД (SQLite+Postgres) | Низкая | Высокое | Idempotent ALTER как уже принято; тест на обеих СУБД |
| Битый ключ бизнеса роняет ответы | Средняя | Среднее | Router: невалидный BYOK → fallback на глобальный + флаг ошибки в UI |
| Рост стоимости на платформенных ключах | Высокая | Среднее | BYOK + учёт токенов (Этап 5) |
| Ввод ключа через чат (нарушение правила) | Низкая | Высокое | Ключ вводится только в UI-форме, никогда в диалоге |

## 6. Файлы, которые будут изменены/добавлены

**Новые:**
- `ai_providers.py` — реестр провайдеров и их реализации.
- `ai_router.py` — разрешение провайдера/ключа/модели с failover.
- `web/ai-settings.html` — UI управления провайдерами (Этап 3).

**Изменяемые:**
- [`ai.py`](ai.py) — `_ask`/`_providers`/`ping` делегируют Router; провайдер-функции переезжают (Этапы 0–1).
- [`database.py`](database.py) — миграция `ai_credentials` + CRUD + шифрование (Этап 2).
- [`config.py`](config.py) — `AI_KEYS_SECRET`, `AI_BYOK_ENABLED`, дефолтные провайдер/модель.
- [`server.py`](server.py) — эндпоинты AI-настроек; прокидывание `business` в вызовы (Этап 3).
- `web/nav.js` / `settings.html` — ссылка на новую страницу.
- `.env.example`, `.env.production.example` — новые переменные.
- `schema.sql` — декларативно описать `ai_credentials` (для свежих БД).

**Не трогаем:** RAG (`search_chunks`, `_chunk_text`), диалоговую логику `botcore.py`/`bot.py`, промпты по существу, trial-систему.

## 7. Порядок внедрения (сводка)

1. **Этап 0** — рефактор провайдеров в модуль, поведение 1-в-1.
2. **Этап 1** — Router поверх глобального дефолта, убрать глобальный `_active`.
3. **Этап 2** — таблица `ai_credentials` + шифрование, за фича-флагом (выкл).
4. **Этап 3** — UI + эндпоинты, включить BYOK; без ключа → платформенный дефолт.
5. **Этап 4** — новые провайдеры в реестр по мере надобности.
6. **Этап 5** — маршрутизация по задачам и учёт стоимости (позже).

Гарантии на каждом шаге: обратная совместимость (пустой BYOK = сегодняшнее поведение), отдельная тестируемость, откат через фича-флаг.
