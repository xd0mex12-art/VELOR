# Промт: связать демо-клинику и завести ей отдельный кабинет

Скопируйте всё, что ниже разделителя, в новую сессию Claude Code, открытую
в папке проекта VELOR.

---

<role>
Ты — senior backend-инженер на живом продукте VELOR AI (мультиарендный
ИИ-ассистент для малого бизнеса: Python 3.12 / FastAPI / SQLite локально и
PostgreSQL в бою / чистый HTML+JS без сборки).

Правило работы одно: **улучшать, не ломая**. Продукт продаётся, у него 3264
зелёные проверки, и ни одна из них не должна покраснеть.
</role>

<hard_rules>
1. **Схему базы не менять.** Ни новых таблиц, ни новых колонок. Всё, что нужно
   для этой задачи, в схеме уже есть — если кажется, что не хватает, ты не
   дочитал `database.py`.
2. **Мультиарендность — красная линия.** Каждая строка каждой таблицы несёт
   `business_id`. Любой запрос без него — ошибка. Демо-бизнес не должен видеть
   чужих данных, а чужие — его.
3. **Ноль подделок.** Нельзя дописывать в демо готовые выводы, находки,
   тексты брифингов или «инсайты». Всё, что VELOR говорит о клинике, он обязан
   вывести сам из данных детекторами в `initiatives.py`. Ты кладёшь факты —
   выводы делает продукт. Если после твоих правок находка исчезла, значит
   данные перестали её порождать; чинить надо данные, а не дописывать вывод.
4. **Продукт не подгонять под демо.** Если демо выглядит плохо — виноват набор
   данных, а не код продукта. Единственное исключение — если ты нашёл
   настоящую ошибку продукта; тогда останавливаешься и говоришь о ней отдельно,
   не смешивая с этой задачей.
5. **Язык русский**, живой, без канцелярита. Комментарии объясняют «почему»,
   а не пересказывают код. Термины продукта: «возможность» (не lead в тексте),
   «находка», «полномочия».
6. Новых зависимостей не добавлять.
</hard_rules>

<what_exists>
Демо-набор уже написан: **`tools/demo_dental.py`** (420 строк). Он создаёт
отдельный бизнес «Демо: стоматология «Дентарика»» и наполняет его.

Ключевые вещи, которые надо знать и сохранить:

- `MARK = "demo-dental"` — метка в поле `source` каждой созданной строки.
- `BADGE = "[ДЕМО-НАБОР VELOR]"` — метка в `about` самого бизнеса.
- `--clean` удаляет бизнес, **только** если `about` содержит `BADGE` **и** имя
  точно равно `NAME`. Эту защиту не ослаблять: она стоит между «убрать демо» и
  «стереть живого клиента».
- `random.seed(20260906)` — набор воспроизводим. Оставить.
- Строители: `_clients`, `_routine` (≈240 плановых приёмов), `_history`,
  `_windows` (две недели «до» и «после» — на них держится замер конверсии),
  `_waiting` (3 обращения без ответа), `_money` (аренда, зарплаты, материалы).

Сейчас набор порождает четыре находки без единой подсказки, и это надо
сохранить:

```
• 7 клиентов перестали возвращаться
• Покупают реже: 40% вместо 70%
• Потеряно 6 возможностей
• 3 горячих клиента ждут ответа
```
</what_exists>

<the_problem>
Я собрал набор в песочнице и померил связность. Числа:

| | |
|---|---|
| пациентов | 34 |
| **сообщений на всю клинику за 3 месяца** | **11** |
| возможностей | 51 |
| заявок | 251 |
| движений денег | 266 |

Чего не связано:

| | |
|---|---|
| пациентов без единого сообщения | **31 из 34** |
| возможностей без разговора (`first_message_id` пуст) | **51 из 51** |
| выигранных возможностей без заявки (`order_id` пуст) | **35 из 35** |
| заявок, не привязанных ни к одной возможности | **251 из 251** |

Собственная сверка продукта — `leads.reconcile(business_id)` — находит на этом
наборе **48 противоречий**:

```
won_without_order     35   Возможность выиграна, но заявки за ней нет.
lost_without_reason   13   Возможность закрыта без причины.
```

Второе — отдельная ошибка набора: `_lead()` пишет в `lost_reason` человеческий
текст («дорого», «ушёл в другую клинику»), а продукт ждёт код из
`leads.LOST_REASONS`. Из-за этого разбор «почему теряем» не группируется.

Итог: клиника выглядит как таблица чисел без историй. Заявки висят сами по
себе, возможности не помнят разговора, из которого родились, а переписки
почти нет вовсе.
</the_problem>

<task>
## 1. Связать всё

- **Каждая выигранная возможность** должна ссылаться на настоящую заявку:
  `leads.order_id` → существующая строка `orders`. И обратно: заявка, выросшая
  из возможности, должна быть той же самой, что записана в `order_id`.
- **Каждая возможность** должна помнить разговор: `first_message_id` и
  `last_message_id` указывают на настоящие строки `messages` того же клиента и
  того же бизнеса.
- **Проигранные** — только коды из `leads.LOST_REASONS`. Человеческий текст,
  если он нужен, кладётся в `meta`, а не в `lost_reason`.
- Приёмы «из потока» (`_routine`) возможностями обрастать **не должны** — их и
  в жизни нет: человек записался по телефону или по плану лечения. Не надо
  привязывать всё ко всему ради красивой цифры; связь должна быть настоящей.

## 2. Придумать переписку

Сейчас 11 сообщений на 34 пациента. Нужна нормальная история: большинство
пациентов должны иметь разговор, из которого видно, как они пришли.

Требования к диалогам:

- Пишет **живой человек**, а не шаблон: короткие фразы, опечатки уместны,
  вопросы про цену, страх боли, «а можно в субботу», «а рассрочка есть».
- Стоматология настоящая: гигиена, лечение кариеса, удаление, импланты,
  брекеты, коронки, детский приём. Прайс уже есть в `SERVICES` — цены в
  разговоре обязаны совпадать с ним.
- Разговоры разложены по времени в те же 90 дней, что и остальной набор, и
  **согласованы** с ним: если человек записался и пришёл — сообщение раньше
  визита, а не позже.
- Роли честные: `role='user'` — пациент, `role='assistant'` — ответ клиники.
- Три обращения из `_waiting` должны остаться висящими без ответа: на них
  держится находка «3 горячих клиента ждут ответа». Не «почини» их случайно.

Не надо 34 одинаковых диалога. Пусть будет разное: кто-то спросил цену и
пропал, кто-то записался с первого сообщения, кто-то торговался, кто-то
вернулся через два месяца.

## 3. Отдельный кабинет

**Ты делаешь ОТДЕЛЬНЫЙ кабинет — новый бизнес рядом с существующими, а не
правку чьего-то.** Ни один другой `business_id` в базе не должен измениться.

**Логин и пароль придумай сам.** Логин — читаемый и относящийся к клинике.
Пароль — случайный, стойкий, не словарный. Оба выведи в конце работы одним
блоком, чтобы их можно было скопировать:

```
Кабинет демо-клиники
  адрес:  /login.html
  логин:  …
  пароль: …
```

Пароль нигде не сохраняется в открытом виде, кроме этого вывода — в базе он
лежит хешем, этим занимается `database.create_business`.
</task>

<acceptance>
Работа считается сделанной, когда ВСЁ из списка выполняется на свежесобранном
наборе. Проверь каждое сам, числами, а не на глаз:

1. `leads.reconcile(bid)` возвращает **пустой список**. Ноль противоречий.
2. Возможностей без `first_message_id` — **ноль**.
3. Выигранных возможностей без `order_id` — **ноль**, и каждая ссылается на
   существующую заявку того же бизнеса.
4. `lost_reason` у всех проигранных — из `leads.LOST_REASONS`.
5. Пациентов без переписки — не больше пяти из 34, и у каждого «пропавшего»
   есть причина, понятная из данных.
6. `initiatives.scan(bid)` по-прежнему сам порождает **все четыре** находки из
   `<what_exists>`. Ни одна не дописана руками.
7. Финансовая картина осталась правдоподобной: выручка около 1,3 млн ₽ за
   период, прибыль положительная. Клиника, работающая в убыток, — это другой
   демо-набор, не этот.
8. `python tools/demo_dental.py --clean` убирает демо целиком и **ничего**
   кроме него. Проверь: заведи рядом обычный бизнес, прогони `--clean`, убедись
   что он на месте.
9. `python tests/run_all.py` — **3264 успешно, 0 провалено** или больше.
   Меньше быть не может: если проверок стало меньше, ты что-то удалил.
</acceptance>
